Salt만으로 충분한가?

SHA-256과 bcrypt의 비밀번호 후보 검증 비용 비교

  • 작성자: 편승훈
  • 작성일: 2026-10-14
  • 관심 분야: 비밀번호 저장 보안과 오프라인 추측 공격

초록

본 연구는 비밀번호에 salt를 적용하는 것만으로 충분한 추측 비용이 확보되는지에 대한 의문에서 출발했다. 동일한 PC와 가상 후보 32개를 사용해 단일 salted SHA-256과 bcrypt(cost 12)의 검증 비용을 각각 10회 측정했다. 후보당 평균 검증 시간은 SHA-256이 0.744μs, bcrypt가 185.631ms였으며, bcrypt가 약 249,357배 길었다. 10회 모두 bcrypt의 후보당 시간이 더 길어 원래 가설은 지지되지 않았다. 결과는 salt의 존재와 후보당 계산 비용을 구분해야 한다는 해석을 뒷받침한다. 다만 한 PC와 특정 구현의 반복 측정이므로 실제 공격자의 GPU 성능이나 모든 비밀번호의 안전성으로 일반화할 수 없다.

1. 서론

1.1 문제의식

비밀번호를 해싱하고 salt까지 적용하면 어떤 해싱 방식을 사용하더라도 안전할 것이라고 생각했다. 그러나 해시가 유출된 경우 공격자는 로그인 서버에 요청하지 않고 후보 비밀번호를 계산하여 비교할 수 있다. 따라서 저장값이 서로 다르게 나타나는 것과, 후보 하나를 검사하는 비용이 높다는 것은 구분할 필요가 있다.

Provos와 Mazières는 계산 비용을 조절할 수 있는 bcrypt를 제안하고, 기존 비밀번호 해싱 방식의 평가와 처리량 비교를 제시했다[1]. NIST는 salt와 적절한 비밀번호 해싱 방식을 함께 사용하여 오프라인 추측 비용을 높일 것을 요구한다[2]. OWASP는 빠른 SHA-256 단독 사용이 비밀번호 저장에 부적합하다고 설명하고 전용 비밀번호 해싱 방식을 권고한다[3].

1.2 주제 선정 과정

다음 질문 10개를 검토했다.

  1. 같은 비밀번호에 다른 salt를 사용하면 해시가 달라지는가?
  2. salt 길이가 SHA-256 검증 시간에 어떤 영향을 주는가?
  3. salted SHA-256과 bcrypt의 후보 검증 속도는 얼마나 다른가?
  4. bcrypt cost가 증가하면 검증 시간이 어떻게 변하는가?
  5. 비밀번호 길이가 검증 시간에 어떤 영향을 주는가?
  6. 후보 개수가 증가하면 전체 검증 시간이 어떻게 변하는가?
  7. CPU 작업자 수에 따라 처리량이 어떻게 달라지는가?
  8. 온라인 로그인 제한이 반복 요청을 얼마나 차단하는가?
  9. SHA-256 라이브러리에 따라 속도가 얼마나 달라지는가?
  10. 다른 PC에서 실행하면 결과가 얼마나 달라지는가?

최종 주제로 3번을 선택했다. salt가 있어도 해싱 방식의 계산 비용이 중요한지 직접 확인할 수 있고, 하루 안에 가상 데이터로 측정할 수 있기 때문이다. 1번은 salt의 효과를 확인하는 보조 검사로 포함했다.

보류한 후보와 이유는 다음과 같다.

  • salt 길이 비교: 해싱 방식 자체의 비용 차이에 집중하기 위해 보류했다.
  • 작업자 수 비교: 병렬 실행 효과가 섞이지 않도록 단일 작업자로 고정했다.
  • 온라인 로그인 제한: 네트워크와 서버 정책을 제외하고 계산 비용을 측정했다.

1.3 연구 가설

동일한 PC와 가상 비밀번호 후보 집합에서, salt를 적용한 단일 SHA-256의 후보당 검증 시간은 bcrypt(cost 12) 이상일 것이다.

‘안전하다’라는 넓은 표현을 직접 측정할 수 있는 후보당 검증 시간으로 좁혔다. SHA-256의 시간이 bcrypt보다 짧다면 가설과 반대되는 결과로 다루며, 차이가 측정 변동에 비해 불명확하면 판단을 유보하기로 했다.

1.4 알려진 사실과 직접 확인할 내용

문헌은 salt와 계산 비용의 역할이 다르다는 배경을 제공한다. 본 연구는 새로운 암호학적 사실을 제안하는 대신, 선택한 PC와 구현에서 두 방식의 검증 시간과 처리량 차이를 직접 확인한다.

2.3 측정 범위

측정에는 후보 순회, 해싱 또는 checkpw 호출, 비교와 일치 수 집계가 포함된다. 목표 해시 생성, 파일 저장, 후보의 문자열 사전 변환은 제외했다.

계산식은 다음과 같다.

  • 후보당 검증 시간 = 총 검증 시간 ÷ 실제 검증 횟수
  • 초당 검증 수 = 실제 검증 횟수 ÷ 총 검증 시간(초)

SHA-256은 한 번의 순회 시간이 짧아 교정 실행으로 약 1초 분량의 반복 수를 정했다. 본실험에서 후보 목록을 43,570번 순회하여 측정당 1,394,240회를 검증했다. bcrypt는 후보 목록을 한 번 순회하여 측정당 32회를 검증했다.

두 방식은 검증 횟수가 다르므로 총시간만 비교하지 않고 횟수로 정규화한 지표를 비교했다.

  3. 준비 실행과 SHA-256 반복 수 교정
  4. 예비 측정 후 본실험 조건 확정
  5. 각 방식 10회 측정, 실행 순서를 번갈아 배치
  6. 각 측정값을 CSV에 즉시 저장

초기 논의에서는 각 방식 5회를 제안했으나, 세부 과제 기준을 확인하고 본실험 전에 10회로 변경했다. SHA-256 반복 수는 예비 실행에서 정하고 본실험 동안 고정했다.

3. 결과

3.1 salt 보조 검사

동일한 가상 비밀번호에 서로 다른 salt를 적용한 결과, SHA-256과 bcrypt 모두 서로 다른 저장값이 생성됐다. bcrypt의 두 저장값은 원래 가상 비밀번호로 모두 검증됐다.

이 결과는 해당 입력에서 salt가 저장값을 다르게 만든다는 것을 보여 준다. 사전 계산 공격의 효과 전체를 측정한 실험은 아니다.

보조 검사 원자료는 data/salt-check.json에 보관했다.

표시값은 반올림했으며, 비율 계산에는 반올림 전 값을 사용했다. 평균 초당 검증 수는 각 측정의 처리량을 산술평균한 값이다.

bcrypt의 평균 후보당 시간은 SHA-256의 약 249,356.63배였다. 같은 반복 번호로 비교했을 때 10회 모두 bcrypt가 더 느렸다.

3.3 가설 판단

원래 가설은 지지되지 않았다. salted SHA-256의 후보당 시간이 bcrypt 이상일 것으로 설정했지만, 실제 측정에서는 SHA-256이 더 짧았다.

판단의 근거는 data/raw.csv의 elapsed_ns와 checks이다. 원자료 20행을 모두 분석에 포함했으며 제외한 측정값은 없다. bcrypt가 더 빠르게 나온 반복은 없었다. 추가적인 통계적 유의성 검정은 수행하지 않았다.

4. 논의

4.1 salt만으로 충분한가?

보조 검사에서는 두 방식 모두 salt에 따라 저장값이 달라졌다. 그러나 본실험에서는 salt가 있는 SHA-256도 많은 후보를 빠르게 검증할 수 있었다.

이 결과는 salt의 존재만으로 높은 추측 비용이 보장되지는 않는다는 해석을 뒷받침한다. salt는 여러 계정에서 같은 저장값이 나타나는 것과 사전 계산 결과의 재사용을 어렵게 하는 역할을 한다. 후보 하나의 계산 비용을 높이는 역할은 별도로 필요하다[1–3].

4.2 무엇을 사용해야 하는가?

비밀번호 저장에는 salt와 함께 계산 비용을 조절할 수 있는 적절한 전용 비밀번호 해싱 방식을 사용해야 한다.

이번 실험에서는 bcrypt cost 12가 SHA-256보다 높은 검증 비용을 보였다. 그렇다고 모든 신규 시스템에서 bcrypt가 최선이라는 뜻은 아니다. OWASP는 Argon2id를 우선 권고하고, bcrypt는 기존 시스템에서 사용할 때의 조건을 제시한다[3]. Argon2id는 이번 실험에서 측정하지 않았다.

4.3 원래 가설과 반대 결과에 대한 검토

첫째, salt가 저장값을 바꾼다는 효과를 후보당 계산 비용 증가와 같은 것으로 생각했던 점을 재검토했다.

둘째, 실제 검증 횟수가 서로 달라 총시간 비교가 왜곡될 가능성을 확인했다. 분석에서는 실제 횟수로 나눈 시간과 처리량을 사용했다.

셋째, Python 반복문·라이브러리 구현·PC 부하가 결과에 영향을 줄 가능성을 고려했다. 모든 반복을 포함하고 실행 순서를 번갈아 배치했지만, 이 요인들을 완전히 분리하거나 통제한 것은 아니다.

원래 가설은 결과에 맞춰 덮어쓰지 않고 그대로 남겼다. 후속 연구에서는 다른 PC·구현·cost에서 같은 방향의 차이가 나타나는지 검증할 수 있다.

4.4 한계

  • 한 PC와 특정 라이브러리 구현의 결과다.
  • 동일한 목표 해시에 대한 반복 측정이며 독립적인 사용자 표본이 아니다.
  • 후보 집합과 문자열 길이가 제한되어 있다.
  • SHA-256과 bcrypt의 목록 반복 수 및 측정 시간이 다르다.
  • Python 순회·비교·함수 호출 비용이 포함된다.
  • CPU 부하와 발열·클록 변화를 별도로 기록하지 않았다.
  • GPU·다중 작업자·최적화된 공격 도구의 성능은 측정하지 않았다.
  • 실제 비밀번호가 발견될 확률이나 시간을 측정하지 않았다.
  • 온라인 로그인 제한·네트워크·계정 잠금은 검증하지 않았다.
  • bcrypt의 cost는 12 한 가지 조건만 측정했다.

5. 결론

동일한 PC와 가상 후보 집합에서 salt를 적용한 단일 SHA-256과 bcrypt(cost 12)를 각각 10회 측정한 결과, bcrypt의 후보당 평균 검증 시간이 약 249,357배 길었다. SHA-256이 bcrypt 이상으로 느릴 것이라는 원래 가설은 이번 실험에서 지지되지 않았다.

두 방식 모두 서로 다른 salt에서 다른 저장값을 만들었지만, 그 사실만으로 비슷한 추측 비용이 확보되지는 않았다. 따라서 비밀번호 저장에서는 salt의 역할과 후보당 계산 비용을 구분하고, 문헌과 서비스 환경에 맞는 전용 비밀번호 해싱 방식을 선택해야 한다. 다만 이 비율은 특정 환경의 측정값이며, 모든 비밀번호의 안전성이나 실제 공격 환경의 성능을 보장하지 않는다.

  2. 새로운 측정: 기존 자료를 덮어쓰지 않도록 별도 복사본에서 data와 results 폴더를 제외한 코드·문서를 준비한다. python experiment.py --mode pilot python experiment.py --mode main python analyze.py

의존성은 requirements.txt, 환경은 data/environment-main.json, 상세 실행 조건은 data/protocol.json에서 확인한다.

재측정값이 원래 수치와 완전히 같을 필요는 없다. 원자료 보존, 설계 일치, 계산 재현 여부를 확인한다.

부록 B. AI와 나의 판단

① AI에게 맡긴 일: 문헌 탐색, 실험·분석 코드 초안과 논문 구조 작성을 맡겼다.

② 내가 직접 판단한 일: salt만으로 충분한지라는 연구 질문을 제시하고, 내 PC에서 가상 데이터 실험을 실행하여 원자료를 수집했다.

③ AI 제안을 따르지 않은 일: 처음 제안된 단순 속도 비교에서 ‘salt를 넣으면 어떤 해시든 안전한가’라는 의문을 중심으로 연구 질문을 변경했다.
