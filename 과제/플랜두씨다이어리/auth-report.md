# 플랜두씨 다이어리 — 인증 구현 설명서

## ① 무엇으로 붙였나

- 인증 방식: 직접 구현한 서버 세션 인증
- 비밀번호 해싱 라이브러리: bcryptjs 3.0.3
- 저장소: Supabase PostgreSQL
- 배포: Vercel
- 세션 전달: Secure·HttpOnly·SameSite=Strict 쿠키
- 서버에는 세션 원문 대신 SHA-256 해시를 저장한다.

## ② 왜 그걸 골랐나

기존 Vercel API와 Supabase 구조를 유지하면서
로그인 확인, 세션 폐기, 자료 소유자 검사를 직접 구현하기 위해 선택했다.
비밀번호 해싱은 직접 구현하지 않고 bcryptjs를 사용했다.

검토했지만 선택하지 않은 방법:
Supabase Auth — 이번에는 서버 세션의 발급과 폐기 과정을
직접 구현하고 확인하기 위해 선택하지 않았다.

## ③ 어디를 어떻게 고쳤나

- api/_lib/auth.js: 비밀번호 해싱·검증, 세션 관리, 인증 공통 처리
- api/auth.js: 가입·로그인·로그아웃·계정 삭제
- api/plans.js: 로그인 사용자 소유의 계획만 접근 허용
- api/tasks.js: 연결된 계획의 소유자 검사
- api/logs.js: 연결된 할 일과 계획의 소유자 검사
- diary-auth.js: 로그인 확인, 로그아웃, 계정 삭제 화면 처리
- 데이터베이스: 사용자·세션 테이블과 계획의 owner_id 추가
- 기존 자료: 본인이 작성한 계획을 본인 계정으로 이전

## ④ 안 열리는 것을 확인한 기록

### 로그아웃 후 기존 세션 재사용

- 검사일: 2026-10-08 KST
- 요청: GET /api/plans
- 요청 쿠키: __Host-pds_session=[가림]

로그인 상태의 세션 쿠키를 PowerShell에 보관했다.
브라우저에서 로그아웃한 뒤 동일 쿠키로 같은 GET 요청을 다시 보냈다.

로그아웃 전: HTTP 200 — 자료 조회 성공

로그아웃 후: HTTP 401

응답:
{"error":{"code":"unauthorized","message":"세션이 만료되었거나 로그아웃되었습니다."}}

판정: 로그아웃 후 기존 세션으로 자료를 조회할 수 없음을 확인했다.

### B → A 계획 읽기 차단

- 검사일: 2026-10-08 KST
- 로그인 계정: B
- 대상: A 소유의 계획
- 요청: GET /api/plans?id=e44bbdff-df7f-4fa0-a121-7bbf6303131b
- 인증 쿠키: [가림]
- 응답 상태: HTTP 404
- 응답 본문:
  {"error":{"code":"not-found","message":"접근 가능한 계획을 찾을 수 없습니다."}}
- 판정: B 계정에서 A의 계획을 직접 조회하는 요청이 거절됐다.

## ⑤ AI와 나

- AI에게 맡긴 일: 인증 코드 초안과 검사 절차 작성
- 내가 직접 판단한 일: 기존 앱에 인증을 추가하는 방향과 공개 범위 결정
- AI 제안을 따르지 않은 일: 실제로 해당한 내용을 제출 전에 작성한다.

## ⑥ 아직 못 막은 것

- 로그인 실패 횟수 제한과 무차별 대입 방어는 아직 구현하지 않았다.
- 이메일 소유 확인과 비밀번호 재설정 기능은 아직 구현하지 않았다.
- 기존 공개 배포 주소의 접근 차단 여부는 추가 확인이 필요하다.
